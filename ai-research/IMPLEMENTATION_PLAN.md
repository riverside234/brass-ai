## Recommendation and scope

Build a new decision policy, reuse the installed rules engine, and train through search and a diverse population of four-player opponents. The original Hard AI is a handwritten priority system: there are no neural weights to fine-tune. Keep it as a benchmark with zero default training weight. The recovery proposal uses qualified v3 demonstrations and more v3 tables initially, reducing them to 5% of ordinary tables as self-play matures. Do not restrict the new policy to choosing between the old AI's rule outputs.

The starting model remains a shared policy/value network of approximately two million parameters, with a state encoder, candidate-choice encoder, four-seat outcome estimates, and a personality/soft-intent input. Values use one observing player's permitted information, not four combined private views. First implement planning across the current turn and sampled opponent responses; deeper observation-tree search follows only if it improves equal-budget results. Compare smaller and larger models at the same laptop thinking budget. All policy training and strength evaluation games for this project use four players.

The deployment target is offline play on the Core Ultra 5 135U laptop. CPU rules/search workers and optional Intel GPU inference are separate from RTX training on the lab server. The product goal is varied, coherent, fair opponents with Easy, Medium, and Hard settings. New Easy beating stock Hard is a release criterion to demonstrate, not a promised consequence of using machine learning.

## 1. Establish the environment and state restoration

**Deliverable:** a small C# rules host using the installed assembly, with a versioned protocol for training and evaluation. Python controls matches and model training; C# applies the game's rules. Do not rewrite the game engine initially.

Environment operations, implemented by R1 under the JSON names documented in [R1_HOST.md](../docs/R1_HOST.md):

| Operation | Contract |
| --- | --- |
| `ResetFourPlayer(seed, setup)` | Construct a legal four-player game and advance to the first decision. The seed stays inside the trusted environment. |
| `GetDecisionContext()` | Return the actual decision-maker, phase, actions remaining, and revision. A debt decision may belong to a different player from the normal turn owner. |
| `Observe(player)` | Return only that player's permitted information. |
| `LegalChoices(context)` | Return legal next choices, including continuation/finish choices where appropriate. |
| `ApplyChoice(choice)` | Advance a decision inside an isolated simulation; expose whether more choices are required. |
| `ValidateAndApplyAction(plan)` | Validate a complete ordinary action and apply it once at the appropriate boundary. |
| `AdvanceAutomaticPhases()` | Handle draws, turn/round transitions, income, era changes and scoring until another decision or game end. |
| `Checkpoint / Restore / Replay` | Reproduce trusted engine state for validation, debugging and simulation. |
| `GetResult()` | Return final scores, official ordering/tiebreak results, and per-seat learning targets. |

The search layer additionally needs `GenerateTurnPlans(playerView, budget)` and `SampleHypotheticalWorld(playerView, searchSeed)`. The latter must reconstruct from allowed information and constraints, never from the real hidden assignments. `EvaluateTurnPlans` receives sampled worlds and an opponent mixture, advances the actual decision scheduler, and returns utility estimates plus horizon/uncertainty/work metadata. Keep these planning operations separate from authoritative live execution.

Expose stable semantic choice IDs and explicit seat mappings so both the Daiyu-based trainer and `BrassSpielState` adapter use this contract. R4 implements separate pause/resume hooks for setup/deal/reshuffle chance boundaries in its own authored worker. S2 continues resolving those transitions automatically inside hypothetical worlds; the R4 exit suite checks matched full-game transitions against R1 rather than relying on fixture-only validation.

Keep two representations separate: a private **engine checkpoint**, containing the full state needed to reproduce the environment, and a **player observation**, suitable for the policy and search. A full checkpoint must never become the model input or the runtime search request.

Start with one active game per worker process. Build reconstruction from typed commands/events and explicit phase state, including current action progress, pending resource requirements, merchant bonuses and debt dictionaries. Copy event payloads instead of sharing mutable event objects. Audit all relevant statics, then bind them to the active reconstructed game. Use a small persistent process pool for simultaneous branches; each worker reconstructs and evaluates scenarios sequentially. Do not create a new process per rollout or search clones inside the live Unity process while static references can interfere with the live game.

Correctness comes before fast copying. Once reconstruction works, measure replay and snapshot costs; add checkpoints or a compact simulation representation only if profiling justifies it. Search also needs a constructor for **sampled hypothetical worlds** from permitted player information, independently of the real hidden state.

**Exit checks:** replay the same four-player command trace to identical canonical states; restoring and applying a branch leaves the source untouched; isolated workers do not affect each other; restore works at action, bonus, debt and era boundaries. Compare representative complete traces with Unity's actual runtime, because the successful .NET headless probe does not establish Mono/.NET or lab-OS equivalence. Include explicit setup/card data in reproducibility records rather than assuming a numeric seed means identical shuffling on every runtime.

## 2. Implement every legal decision, including action continuations

**Deliverable:** `LegalChoiceProvider`, typed action plans and an executor, shared by training, search and the game adapter.

Represent an action as a sequence of legal decisions. This avoids constructing the full Cartesian product of cards, locations, resources and continuation choices before the policy can make progress. An action plan finishes one ordinary action; a turn plan contains the remaining one or two actions. Search generates complete candidates lazily from the decision tree. The same state/choice scorer can guide partial choices and completed plans, with value estimates at defined settled boundaries.

| Action or phase | Choices and edge cases to cover |
| --- | --- |
| Build | Card from the acting hand; city/slot; industry and available tile; overbuilding; exact coal/iron sources and resource consumption order; market access and affordability. |
| Network | First link; resource payment; optional second rail link or stopping; coal and beer sources for each required payment; connectivity changes caused by the first link. |
| Sell | Eligible industries and their order; reachable merchants; beer sources; merchant rewards; legal development bonus and completion; when to stop selling. |
| Develop | One or two eligible tiles, chosen in sequence; iron sources/costs; stopping after one; unavailable or undevelopable tiles. |
| Loan and pass | Legal card discard and the action's own restrictions and effects. Passing is an explicit legal move, never a silent response to an adapter error. |
| Scout | Three distinct cards from the original hand. The engine splits this into the normal one-card discard and a two-card exchange; also check wild-card restrictions and supply. |
| Forced liquidation | Correct player and ownership; eligible industries; remaining debt; completion with no industries left; resulting VP loss. |
| Turn/round/era transitions | First-round one-action rule, later two-action turns, card replenishment at the correct point, spending-based turn order, income, scoring, removal and era setup. |

Use the engine's action APIs and relevant UI preconditions, but do not treat exceptions as a complete legality oracle: some lower-level methods assume the caller already checked ownership, hand membership or a valid action phase. Inspect and enforce those preconditions in the adapter. Do not call an old helper that silently picks another resource or link after the model has selected a plan.

UI preconditions also contain audited defects. Cross-check against the selected rules contract and independent fixtures; agreement between a buggy UI and a buggy engine is not proof of legality.

Give board elements stable semantic identifiers. Keep transport handles separate from model features. Equivalent duplicate cards or choices may be grouped only after confirming that doing so preserves every strategically distinct resulting state.

The legal provider must represent every legal alternative. Search is allowed to examine only a subset within its time budget, but that pruning belongs to search and must not be confused with the rules interface. Use progressive expansion to control large branching factors, retaining a way to explore alternatives outside the initial preferred candidates.

Add a `TurnPlanGenerator` with a complete incumbent, bounded proposal beam, explicit enabling-action coverage and progressive widening. A weak-looking loan/development must survive long enough to evaluate its useful second action. Generate the continuation from the resulting state and remaining hand; keep card opportunity cost and source choices. Compare both orders where appropriate and avoid duplicate plans without collapsing strategically different remaining cards or histories.

**Exit checks:** hand-constructed rule fixtures for every row above; exhaustive enumeration on small constrained states; legal alternatives cross-checked with the human UI and rule preconditions; randomized four-player games checking progress and state invariants. Check cards, cash, resources, ownership, action counts and terminal scoring. Invalid plans must be rejected without changing the source. Detect dead ends and duplicate confirmations explicitly instead of masking them with passes.

## 3. Enforce the information boundary

**Deliverable:** an allowlisted observation schema and a hidden-state sampler with automated information-leak tests.

Include public board/layout, links, industries and resources, public player tracks and available tiles, permitted public history, turn order, era, decision phase, actions remaining, visible counts, and the acting player's hand. Verify public fields against what a human is allowed to see in this client. Retain card/action history only when it is legitimately visible or inferable.

Include round spending because it affects the next order. Keep stable player identity separate from current order and verify value-head/seat remapping after reordering. Treat initial face-down discard identities as hidden even from their nominal owner; their presence in an engine discard collection does not make them observable. If a loaded game lacks legitimate public history, preserve uncertainty instead of reading private events to fill it in.

Exclude other hands, exact future deck order, private setup randomness, the real RNG seed/state and hidden event payloads. Do not encode engine object IDs, allocation order or internal cache state as model features. Legal-choice ordering and metadata must also avoid leaking hidden state.

Runtime search receives the permitted observation and public rules context. It samples plausible unseen cards and future draws consistent with that information, including card conservation, visible discards, hidden allocations, setup exclusions, wild cards, era reshuffles and hand counts. It must not start from the real opponent hands or future deck and merely hide them from the policy. Begin with hard constraints and broad behavioral assumptions; treat failure to take an opportunity as weak evidence, not proof an opponent lacked the necessary card.

Adapt Daiyu's card-conservation/wild-card ideas, but construct the unseen pool from public deck composition and allowed history. Shuffling only the actual opponents' cards and deck would leave actual face-down setup discards excluded, which can reveal information. OpenSpiel resampling, evaluator, reset and action/chance callbacks must obey the same boundary; passing a full state to a bot is not made safe merely by supplying an observation method as well.

During a rollout, each simulated player decides from its own permitted observation of that sampled world. The first search system uses fixed masked opponent policies; it does not optimize opponent tree branches using the root's private knowledge. Select one current-turn plan after averaging over scenarios, rather than a different second action for every unrevealed hand. Nonterminal values use the root's allowed observation at the leaf, not an omniscient state. Future sampled draws can affect future choices only after the rules reveal them. A later root action-observation tree is a separate experiment; [SEARCH_DESIGN.md](SEARCH_DESIGN.md) explains its information-set/POMCP foundations and limitations.

**Exit checks:** construct two engine states with the same allowed actor history/hand but different hidden assignments. Observations, root legal choices and policy outputs must match. With independent fixed search randomness and fixed work in deterministic test mode, search must also match. Separately change the root's private hand while preserving a simulated opponent's view and require unchanged opponent action probabilities. Inspect requests, candidate ordering, opaque IDs, caches and face-down discards. Repeat after save/load and era changes. Environment rewards may reflect the eventual outcome; observations and search-derived targets must respect the information available when a decision is made.

**Deliverable:** a locally playable replacement using the complete decision interface, initially with a simple new heuristic policy; no neural training is required to test integration.

Implement the `IAiBehavior` adapter and intercept the behavior factory. Verify runtime patching compatibility before relying on a particular loader. Profiles and benchmark runners declare `player_count: 4`; retain the existing AI path for two-/three-player games and smoke-check that routing when shared hooks change. Do not spend this release's strategy-tuning budget on other player counts.

Longer thinking cannot be a blocking call inside the existing synchronous loop. Add an asynchronous turn coordinator: copy the permitted decision data on the game thread, request a decision from a local worker, keep the UI responsive, then validate and apply the result on the game thread. Do not let a background thread mutate Unity objects or the live rules engine.

Messages carry protocol/model/schema versions, game identity, revision, actor, phase, request ID and deadline. Discard stale responses after loading, restarting or advancing the game. A time limit returns the best complete validated plan found so far; provide a Play Now control once available. Preserve exactly one confirmation per ordinary action and the game's separate end-turn/end-round lifecycle. Forced liquidation needs its own decision hook.

Search plans both ordinary actions together, but commits one complete action at a time. Refresh the real observation and revalidate or revise the second action using the remaining whole-turn deadline. Preserve a validated continuation and reserve measured time for execution and fallback; do not consume all time on action one or start another full allowance for action two. Keep compound-action choices in their proper phase; resource selection and a second rail link do not consume another ordinary action.

Validate a complete plan on an isolated reconstruction before live execution. Capture a tested recovery checkpoint at a safe boundary. If the worker times out or fails before live mutation, use a cached valid choice or validated fallback. If live application unexpectedly fails partway through, restore through the tested game-history/state path and synchronize the UI, or stop that turn visibly; never continue by pretending cancellation undid the move. Exercise injected failures before accepting recovery as reliable.

Keep personality/configuration and reproducible random state in a versioned sidecar keyed by game and seat if the vendor serializer cannot safely persist them. Loaded games must reconstruct the right behavior without attempting to deserialize an unsupported custom AI class. Include clean disable/uninstall behavior.

**Exit checks:** complete four-player matches with one human and three replacements; both eras; save/load between turns and at supported decision boundaries; restart/menu return during thinking; worker crash/timeout; duplicate/stale response rejection; repeated confirmation protection; bonus and debt flows. UI responsiveness must remain acceptable during the longest configured thinking time.

## 6. Train new weights with search and a diverse opponent population

**Deliverable:** a reproducible four-player trainer, checkpoint pool, replay dataset and evaluation reports.

**R2 foundation is implemented:** [R2_TRAINING.md](../docs/R2_TRAINING.md) documents the versioned `four-seat-learning/1.0.0` model, permitted features, fixed four-player runner, masked teacher loss, terminal outcome loss, optional on-policy terminal-reward experiment, safe checkpoint/resume and checked export. Its lab paths default to `/data/not_backed_up/yxu209/ai-training/`. [R2 exit checks](../docs/R2_EXIT_CHECKS.md) qualify this scaffold; they do **not** satisfy this section's later playing-strength exit gate. The default model has 1,897,389 parameters. R3 now supplies permitted style/intent features and frozen external opponents through the same collector. Model/random collection retains its existing zero defaults. Bank trajectories carry terminal outcomes and external-policy provenance; they are not optimal teacher labels or on-policy neural data. [Step 5](../docs/STEP5_LAB_TRAINING.md) now implements the self-play population loop and neural search distillation on this foundation.

Adapt Daiyu's encoder/scorer and batching scaffold, then initialize new weights. Replace its scalar win/margin/actor-score interface with four stable-seat win-share, placement and auxiliary VP predictions. Update data targets, losses, inference messages, search backup, checkpoint signature, exported outputs and reports together. Reject incompatible scalar checkpoints; never divide a root win estimate equally among the other three players. Test observer/seat mapping and repeated decisions before training.

Require four players in every production data-generation, training and evaluation configuration, including rewritten upstream examples. Keep invalid/corrupt records out, but retain valid losing trajectories for value learning; do not import Daiyu's strategy-based data filters as legality rules. Record any selectively weighted expert data separately. The default learning loop is:

1. Begin with audited imitation and a 40% v3 table curriculum, then reduce v3 to 20%, 10% and finally 5% as declared completed-game boundaries are reached. The mature mix is 70% all-current self-play, 25% historical neural and 5% qualified v3 tables. Original Hard is a benchmark with zero training weight. Rotate seats and vary setups. All-new-agent and mixed neural tables both matter.
2. Run games with legal masks, the correct information boundary and the S1/S2 search stages. Search records candidate quality, confirmation results and continuation choices; the eventual game result provides value targets.
3. Train the policy to propose useful choices/turns and the value heads to estimate outcomes for all four seats from an observer's view. Include deployment-like afterstates and rollout horizons; use extra final-score prediction if it helps.
4. Evaluate a frozen candidate against a held-out opponent pool and fresh seeds. Promote useful candidates without deleting diverse older ones merely because their average rating is lower.
5. Rebalance opponents toward weaknesses discovered in the matchup results, while retaining variety and a stable evaluation set.

Use the improved legacy bank to bootstrap economic competence and as occasional diagnostic opponents as self-play matures. The recovery default converges to 95% neural tables and 5% qualified v3 tables; the prior recipe remains in `previous-lab.json`. Freeze opponents within each game and record versions. Keep the frozen Pottery Flex opponent identity out of training, while retaining all legal Pottery choices and balanced industry exploration. Adjust the population using held-out neural matchups. Stock-only wins and imitation of a guide-derived heuristic do not establish broad strength.

This combines the search/learning loop of [Expert Iteration](https://arxiv.org/abs/1705.08439) with a practical population of opponents. Research on [responses to mixtures of policies](https://arxiv.org/abs/1711.00832) motivates using diverse partners to reduce overfitting. We are proposing these ideas for Brass, not claiming a proven optimum or a full game-theoretic equilibrium solver.

Distill some longer server searches into the small policy, preserving the same observation restrictions. Balance teacher effort with the number and diversity of full games. An elimination scheduler's visit counts partly encode allocation decisions; do not blindly use them as policy probabilities. Begin with recommendations or quality-based targets from fresh finalist samples, retain coverage/confidence metadata, and do not mark unexamined choices as failures. Group first-action targets without rewarding the number of enumerated completions, and supervise the chosen second-action continuation as well.

At the beginning, simple heuristic evaluation can bootstrap search before the new value network is informative. Following results 1.0, the recommended recovery experiment is short imitation pretraining from audited, eligible qualified-v3 demonstrations, followed by revised PPO and the declining v3 curriculum in the [training recovery plan](TRAINING_RECOVERY_PLAN.md). Compare against revised PPO without imitation and preserve held-out setup/opponent identities. This requires a distinct full-legal-choice BC loss; existing external-policy replays are not automatically search teachers or on-policy data. Longer-term learning remains driven by self-play and useful confirmed search examples. Pure random-start self-play is a comparison, not a requirement to rediscover every useful economic concept unaided.

A masked-PPO baseline is a useful lower-complexity learning comparison if search is initially expensive. Maintain separate per-seat trajectories or a correct multi-agent formulation. Do not feed four alternating players' observations and rewards into one ordinary single-agent trajectory. During a learner's episode, freeze sampled opponent versions and retain the learner's own action/reward attribution.

Use terminal placement/win outcomes as the principal task signal, with official tie handling and score prediction for extra learning signal. Decide the final balance between winning and improving placement through evaluation. Avoid simplistic rewards that make borrowing, developing, or supplying opponents inherently wrong: these can be sound Brass decisions. At search nodes use the acting player's utility; there is no two-player sign-flip rule and no shared objective for the three bots facing a human.

Replay records contain rules/observation/choice-schema versions, stable seat identity, permitted observation/history, legal choices and candidate turns, search/confirmation targets, sample counts, horizons, opponent-mixture ID, timing, policy version, style/intent and terminal outcomes. Keep full debug state separately in the trusted harness. Separate whole games/setup groups and opponents between training, validation and final tests; do not split correlated positions from one game across those sets.

**Exit checks:** learning outperforms the non-neural baselines at matched inference budgets, generalizes to unseen opponent mixtures and seeds, and avoids information leaks, invalid actions and reproducible policy collapse. Plot a four-player matchup matrix and rank/score results; a single Elo number or a stock-only win rate can hide style-specific weaknesses and nontransitive matchups.

## 8. Optimize the laptop package and run acceptance tests
